함께 붙여 넣은 지시 원문:

```text
목표

사용자가 여러 장의 사진과 원하는 콘셉트를 입력하면, 사진들을 자연스럽고 짜임새 있는 하나의 영상으로 변환하는 앱의 가능성을 검증하라.

이번 작업은 완성된 서비스 구축이 아니라, 실제 사진으로 영상을 생성하고 결과물을 직접 보며 제품의 가능성과 부족한 점을 판단할 수 있는 실행 가능한 프로토타입 제작이다.

1. 제품 범위

여행 전용 앱이 아니다. 사용자는 여행, 일상, 가족, 반려동물, 행사 등 다양한 사진과 서로 다른 콘셉트를 입력할 수 있다.

여행 사진 약 10장은 첫 구현 및 품질 평가에 사용할 테스트 사례다. 여행에 특화된 화면이나 로직을 제품의 전제로 고정하지 마라.

2. 핵심 경험

사용자가 사진을 올리고 원하는 콘셉트를 설명하면 사진과 의도에 맞는 영상이 만들어져야 한다.

단순히 사진을 업로드 순서대로 나열하는 데 그치지 말고 다음을 고려하라.
- 사진의 내용과 관계를 바탕으로 한 장면 선택과 순서
- 시작부터 끝까지 자연스럽게 이어지는 구성
- 장면별 길이, 움직임, 전환의 일관성
- 음악과 영상의 분위기 및 리듬
- 원본 인물과 장소의 특징 보존

사진에서 알 수 없는 사건이나 관계를 사실처럼 지어내지 마라. 창작적 변형은 사용자가 요청한 콘셉트에 따라 구분해서 적용하라.

3. 최소 사용 흐름

사진 업로드 → 콘셉트 입력 → 영상 구성안 확인·간단 수정 → 생성 → 재생·다운로드가 가능해야 한다.

구성안에는 사진 순서, 장면별 연출과 길이, 선택한 스타일을 표시하라. 사용자가 일부 사진을 제외하거나 순서를 바꿀 수 있게 하라.

콘셉트는 자유로운 문장으로 입력받되, 입력이 어려운 사용자를 위한 선택 예시를 제공하라. 예시가 지원 가능한 용도를 제한해서는 안 된다.

첫 테스트 출력 기본값은 세로형 9:16, 약 15~30초의 MP4로 하되 제품 전체의 고정 규격으로 만들지 마라.

4. 영상 생성 접근

원본 사진을 활용한 편집, 사진 속 장면에 움직임을 주는 생성, 애니메이션 등 스타일 변환을 구분해서 검토하라.

처음부터 모든 스타일을 지원할 필요는 없다. 실제 결과물을 만들 수 있는 한 가지 경로부터 끝까지 연결하고, 다른 방식으로 교체·확장할 수 있게 하라.

확대·이동 효과만 적용했다면 AI로 장면을 생성한 것처럼 설명하지 마라. 실제 생성 모델을 사용한 부분과 일반 영상 편집으로 처리한 부분을 명확히 밝혀라.

5. 진행 방식과 권한

현재 작업 환경과 저장소를 먼저 확인하라. 기존 프로젝트가 있으면 구조와 지침을 따르고, 작업 대상이 불명확하면 먼저 물어라.

장문의 기획 문서나 복잡한 아키텍처부터 만들지 말고, 최소 실행 계획을 짧게 제시한 후 구현과 결과 확인을 중심으로 진행하라.

로그인, 결제, 구독, 공개 배포, 다중 사용자 운영 기능은 이번 검증에 필요하지 않다.

외부 생성 서비스가 필요하면 선택 이유, 필요한 계정·권한, 예상 비용과 처리 시간을 설명하라. 유료 호출이나 개인 사진의 외부 전송은 서비스와 범위를 알려 승인받은 뒤 진행하라. 키나 비밀번호를 코드·로그에 저장하지 마라.

테스트 사진이 없으면 요청하라. 그동안 화면과 로컬 처리 흐름을 준비할 수 있지만, 샘플이나 가짜 응답으로 실제 사진 기반 생성 검증을 마쳤다고 보고하지 마라.

음악은 사용 권한이 확인된 음원만 사용하라. 확보하지 못하면 무음으로 검증하고 음악 관련 평가는 미완료로 표시하라.

6. 결과 평가

첫 여행 사진 세트로 실제 영상을 생성하고 다음을 확인하라.
- 사진과 입력한 콘셉트가 결과에 반영됐는가
- 장면 순서와 흐름이 자연스러운가
- 인물이나 장소가 알아보기 어렵게 변형되지 않았는가
- 움직임과 전환에 어색함이나 시각적 오류가 있는가
- 음악이 있다면 장면과 잘 맞는가
- 결과를 다시 만들거나 일부 구성을 바꾸기 쉬운가

생성 시간, 실제 비용 또는 확인 가능한 추정치, 실패 단계와 재시도 내역도 기록하라. 확인한 사실과 예상치를 구분하라.

7. 완료 기준과 보고

내가 직접 실행할 수 있고, 사진 업로드부터 실제 MP4 재생·다운로드까지 한 번 이상 성공해야 한다.

결과 영상과 실행 방법, 적용한 생성 방식, 확인된 한계, 다음에 개선할 가장 중요한 항목 3개를 제시하라. 실행하지 못한 부분은 명확히 표시하라.

작업 종료 전 self-review와 가능한 테스트를 수행하라. PR을 만들었다면 링크와 검증 결과를 보고하고 종료하며, 별도 승인 없이 병합하지 마라.

가장 중요한 성공 기준은 기능의 개수나 문서의 양이 아니라, 실제 결과물을 보고 이 경험을 앱으로 발전시킬 가치가 있는지 판단할 수 있게 만드는 것이다.
```
